# Issue 41 - Epic: Agnostic CVN Schema, JSON Schema, And Parser

## Summary

Epic `#41` continues the project after the CVN generation workflow baseline. Its
goal is to move from generated Pydantic artifacts toward the TFG objective: an
agnostic curriculum data model, a JSON-oriented schema, and a parser/validator
that can import CVN data from PDF, XML, and JSON sources.

This epic must not treat the current generated Pydantic models as the final
conceptual model. They are an implementation source and traceability layer. The
domain model must remain agnostic to XML serialization details.

## TFG Alignment

This epic addresses these TFG phases:

1. propose a low-level format independent from the final representation
2. define a JSON-based schema for text files and NoSQL-like storage
3. develop a Python parser and validator using Pydantic
4. prepare the base for later local storage, LaTeX export, and application work

The guiding principle remains:

- do not model CVN XML structure as the domain
- recover curriculum concepts and preserve CVN traceability
- keep XML, JSON, UML, and Pydantic as representations over a shared semantic
  model

## Problem Statement

The repository now has structural bindings, normalized metadata, semantic policy,
domain generation, and tests. The next problem is to decide how those generated
models can support a representation that is useful beyond Python code:

- a UML or UML-like diagram for agnostic conceptual representation
- a JSON Schema suitable as the project exchange and persistence schema
- a parser/validator capable of importing existing CVN material and validating
  it against the new model

## Research Scope

### Pydantic To UML Or UML-Like Representation

Research how to transform many Pydantic classes into a diagram that is useful for
agnostic modeling.

Candidate approaches include:

- code-analysis tools such as Pyreverse for Python class diagrams
- text diagram formats such as PlantUML or Mermaid class diagrams
- a custom extractor over Pydantic model metadata
- a custom conceptual intermediate representation that removes Python/XML noise
  before rendering UML

The research must explicitly compare code-centric diagrams with conceptual
domain diagrams. If code-centric tools produce noisy output, the epic should
prefer an intermediate conceptual model and generate UML from that.

### Pydantic To JSON Schema

Research and implement JSON Schema generation from the domain Pydantic layer.

Relevant Pydantic v2 entry points include:

- `BaseModel.model_json_schema()`
- `TypeAdapter.json_schema()`
- `pydantic.json_schema.models_json_schema(...)`

The expected schema baseline is JSON Schema Draft 2020-12, aligned with the
current Pydantic JSON Schema support.

### Parser And Validator Inputs

The parser/validator must support these input families:

1. CVN PDF generated by FECYT, extracting embedded XML when available
2. CVN XML directly
3. Open CVN JSON directly

The PDF path should first attempt deterministic XML extraction from embedded
files or PDF metadata. OCR or LLM-based PDF reconstruction is not part of the
first parser acceptance path unless explicitly planned later.

## Architecture Direction

The intended architecture is:

```text
generated domain Pydantic models + trace metadata
-> conceptual model inventory
-> agnostic UML/diagram representation
-> JSON Schema generation
-> parser/validator for PDF/XML/JSON inputs
```

The parser direction is:

```text
PDF CVN -> extract embedded XML -> XML import path
XML CVN -> structural parse -> normalized/domain mapping -> Pydantic validation
JSON CVN -> JSON Schema/Pydantic validation -> domain object
```

## Parser Import Contract

The parser should eventually expose a clear contract similar to:

- `parse_cvn_pdf(...)`
- `parse_cvn_xml(...)`
- `parse_open_cvn_json(...)`
- `validate_open_cvn_json(...)`

All paths should return a common result shape with:

- parsed domain data
- source format
- validation status
- trace metadata
- structured errors or warnings

## Known Risks

- Python class diagrams may be too implementation-heavy for agnostic UML
- generated Pydantic models may expose too much CVN/XML structure
- PDF CVN XML extraction depends on how FECYT embeds or stores XML in PDFs
- JSON Schema may need custom generation to preserve semantic trace and version
  metadata cleanly
- XML import may need explicit mapping from structural CVN XML to the domain JSON
  shape

## Out Of Scope

- full desktop or web application implementation
- SQLite persistence
- LaTeX export and PDF rendering
- LLM-based import from PDFs without embedded XML
- manual editing UI for curriculum versions

Those concerns belong to the later application epic.
